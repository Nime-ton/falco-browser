Техническая документация проекта: Falco (ранее UltraLight Browser)
====================================================================
Дата актуализации: 21.10.2026
Язык: Rust. Платформа в первую очередь: Windows (WebView2). macOS/Linux — теоретически, не проверялось.

Как читать этот документ: разделы 1–3 — что это и как запустить; 4–8 — как всё устроено;
9 — почему сделано именно так; 10 — известные ограничения; 11 — статус проверки;
12 — идеи развития; 13 — памятка тому, кто будет менять код.


====================================================
1. Что это за проект
====================================================
Falco — маленький нативный десктопный браузер. Это не новый движок: страницы рисует системный
веб-движок (на Windows — Microsoft Edge WebView2, на macOS/Linux — WebKit), а наш код — это
окно, вкладки, адресная строка и блокировщик рекламы.

Зачем он нужен:
  - убрать из браузера всё лишнее: телеметрию, фоновые службы, десятки процессов;
  - держать потребление оперативной памяти как можно ниже (цель — размер порядка одной вкладки
    обычного браузера; реальные замеры ещё не делались, YouTube и подобные сайты сами по себе тяжёлые);
  - встроенно и без расширений блокировать рекламу (в том числе на YouTube и на сайтах с
    навязчивыми баннерами);
  - сохранить совместимость с современными сайтами (YouTube, видеохостинги).

Ключевая идея архитектуры — «один WebView на все вкладки». Вместо отдельного движка на каждую
вкладку у нас ровно один WebView, а «вкладки» — это просто список адресов в памяти Rust.
Переключение вкладки = переход единственного WebView на другой адрес. Интерфейс вкладок и
адресная строка нарисованы поверх страницы внедрённым JavaScript.

Плюсы: очень мало памяти и процессов, минимум кода, нет тяжёлых GUI-библиотек.
Минусы (подробно в разделе 10): при переключении вкладка перезагружается, история переходов
общая для всех вкладок, интерфейс живёт внутри страницы и должен защищаться от сайтов,
которые трогают DOM.


====================================================
2. Что сейчас умеет браузер
====================================================
  - Окно приложения без тяжёлых UI-фреймворков (tao + wry).
  - Постоянный профиль: куки, кэш и сессии сохраняются между запусками (папка browser_profile).
  - Вкладки: создать, переключить, закрыть; панель вкладок со счётчиком на сайт.
  - Всплывающая панель: ряд вкладок + кнопки Назад / Вперёд / Обновить + адресная строка.
    Вызывается наведением мыши на верхний край окна или Ctrl+L.
  - Адресная строка понимает адреса и поисковые запросы (запрос уходит в DuckDuckGo).
  - Многоуровневый блокировщик рекламы (раздел 6).
  - Отдельная защита и ускорение для YouTube: вырезание рекламы из данных, запасной
    скипер, принудительный H.264 (раздел 7).
  - Ручное скрытие любых элементов на странице по клику (Ctrl+Shift+X) — правила запоминаются.
  - Блокировка автозапуска видео средствами самого движка (with_autoplay(false)).


====================================================
3. Требования, структура проекта и сборка
====================================================
Что нужно для сборки:
  - Rust (stable) и Cargo.
  - Windows: Visual Studio Build Tools (C++) и Windows SDK — нужен rc.exe для вшивания иконки.
  - Для запуска на Windows: WebView2 Runtime (в Windows 11 и свежей Windows 10 уже установлен).

Зависимости (Cargo.toml):
  - wry 0.35.0    — обёртка над системным веб-движком.
  - tao 0.23.0    — окно и цикл событий. Версия намеренно зафиксирована на 0.23 из-за
                    совместимости с wry 0.35.0; обновлять только вместе.
  - image 0.24    — только фича png; нужна, чтобы прочитать icon.png для иконки окна.
  - winres 0.1    — build-зависимость; вшивает icon.ico в exe (только Windows).
Имя пакета в Cargo: Falco (так видно в логах сборки). Заголовок окна в коде задаётся в
WindowBuilder::with_title(...).

Структура папки проекта:
  Cargo.toml          манифест проекта
  Cargo.lock          зафиксированные версии зависимостей
  build.rs            скрипт сборки: вшивает иконку в exe (winres)
  icon.ico            иконка exe (настоящий ICO с несколькими размерами внутри)
  icon.png            иконка окна (PNG 256x256 с прозрачностью)
  src/main.rs         весь код браузера: Rust + встроенный JavaScript
  Instruction_manual.txt   этот документ
  browser_profile/    создаётся при первом запуске (профиль: куки, кэш, сессии)
  target/             результаты сборки (в репозиторий не кладём)

Сборка:
  cargo build --release
Готовый файл: target\release\<имя пакета>.exe

Рекомендуемый профиль релиза в Cargo.toml (максимальная оптимизация, меньший exe):
  [profile.release]
  opt-level = 3
  lto = "fat"
  codegen-units = 1
  panic = "abort"
  strip = true
Рекомендуется также первой строкой main.rs поставить:
  #![windows_subsystem = "windows"]
чтобы не открывалось чёрное окно консоли (но тогда не видны println! и тексты паник —
для отладки строку можно временно закомментировать).
Заметьте: скорость страниц определяет WebView2, а не Rust; эти флаги ускоряют запуск и уменьшают
размер exe, но не «разгоняют» сайты.

Важно про папку профиля: путь browser_profile относительный, то есть берётся от рабочей папки
процесса. Если запускать exe из разных мест (ярлык, терминал), профили получатся разные и куки
«пропадут». Это известный недочёт (раздел 12).

Иконки:
  - Иконка exe (проводник, ярлык, панель задач): build.rs + крейт winres, файл icon.ico в корне
    проекта. Если сборка падает с ошибкой RC2135 «file not found: icon.ico» — файл лежит не там
    или называется иначе (частый случай: скрытое расширение, имя icon.ico.png).
  - Иконка окна (заголовок и Alt+Tab): через tao::window::Icon и include_bytes!("../icon.png").
    Описана в рекомендациях, но в текущей версии main.rs может быть ещё не подключена —
    проверьте WindowBuilder::with_window_icon(...).


====================================================
4. Общая архитектура
====================================================
Два слоя, которые общаются через мост IPC:

  [Rust: src/main.rs]  <---- IPC (строки) ---->  [JavaScript внутри страницы]
   - окно (tao)                                     - панель вкладок, адресная строка
   - единственный WebView (wry)                     - блокировщик рекламы
   - список вкладок Vec<String>                     - защита интерфейса от сайтов
   - профиль на диске (WebContext)                  - YouTube-оптимизации

Rust-сторона:
  1. Создаёт окно (tao) и единственный WebView (wry).
  2. Подключает постоянный профиль: WebContext::new(Some("browser_profile")).
  3. Вставляет в каждый загружаемый документ initialization script — большой JavaScript, который
     хранится в main.rs как r#"..."#. Перед вставкой Rust подставляет в него список рекламных
     доменов (метка __AD_HOSTS__).
  4. Хранит вкладки: tabs: Vec<String> (адреса) и current_tab: usize (индекс активной).
  5. Слушает IPC-сообщения от JavaScript и управляет состоянием.
  6. Управляет страницей через webview.evaluate_script(...) — выполняет JS в текущей странице
     (например, сменить адрес или перерисовать панель вкладок).
  7. На Windows передаёт движку аргументы запуска: блокировка рекламных доменов на уровне DNS.

JavaScript-сторона (initialization script) выполняется в каждом документе, включая iframes, ещё до
скриптов самого сайта. Всё, что ниже строки «if (window !== window.top) return;», работает только
в главном окне (интерфейс браузера, горячие клавиши, ручное скрытие). Всё, что выше, действует и
во фреймах (блокировка запросов, YouTube-хуки).

Стартовая страница: https://duckduckgo.com (и у новой вкладки тоже).


====================================================
5. IPC-протокол (сообщения JS -> Rust)
====================================================
JavaScript отправляет строки через window.ipc.postMessage(...). Rust принимает их в
with_ipc_handler, пересылает в цикл событий (UserEvent) и обрабатывает:

  SYNC_URL|<адрес>   Страница сообщает свой текущий адрес. Rust записывает его в tabs[current_tab].
                     Отправляется при загрузке страницы и при изменении адреса внутри сайта (SPA).
                     Только из главного окна — iframes не должны портить список вкладок.
  GET_TABS           Запрос списка вкладок. Rust отвечает вызовом window.renderTabs('<адреса
                     через |||>', <индекс активной>).
  new_tab            Добавить вкладку (duckduckgo.com), сделать активной, перейти на неё.
  SWITCH_TAB|<n>     Сделать активной вкладку n и перейти на её адрес.
  CLOSE_TAB|<n>      Закрыть вкладку n; значение -1 означает «текущую». Если вкладка последняя —
                     приложение закрывается. Если закрыта активная — открывается соседняя.
  next_tab           Перейти на следующую вкладку по кругу.

Rust -> JS: только evaluate_script. Все строки, подставляемые в JS, проходят через js_str()
(экранирует обратный слэш и апостроф, убирает переводы строк), иначе адрес с апострофом ломал бы
скрипт.


====================================================
6. Блокировщик рекламы (слои, от самого раннего к самому позднему)
====================================================
Слой 1. DNS движка (только Windows).
  Список AD_HOSTS из main.rs превращается в правила --host-resolver-rules ("MAP домен ~NOTFOUND,
  MAP *.домен ~NOTFOUND") и передаётся WebView2 через with_additional_browser_args. Рекламные домены
  просто не разрешаются — отсекаются любые запросы к ним (script, iframe, img, XHR), без участия JS.
  Свои аргументы в wry заменяют стандартные, поэтому стандартный
  --disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection указан явно.

Слой 2. Сетевые вызовы в JS.
  Перехватываются fetch и XMLHttpRequest. Запрос блокируется, если адрес совпал с регулярным
  выражением adRegex (подстроки вроде /pagead/, adfox, adriver, popads и т.д.) или его домен/поддомен
  есть в AD_HOSTS. Для fetch возвращается пустой ответ 204. Учитывается, что fetch может получить
  объект Request, а не строку.

Слой 3. Элементы DOM (на всех сайтах, кроме YouTube).
  - Присвоение src у script / iframe / img / embed блокируется (через переопределение сеттеров).
  - Element.setAttribute('src' | 'href' | 'data') для script/iframe/img/embed/object/link/source
    блокируется, если адрес рекламный.
  - navigator.sendBeacon к рекламным доменам подавляется.
  - Невидимые «ссылки-кликеры» (создана скриптом, не вставлена в страницу, target=_blank, без
    download) — классика pop-under рекламы — не кликаются.
  - window.open всегда возвращает null (всплывающие окна запрещены).
  - MutationObserver удаляет рекламные script/iframe/img/embed, которые страница вставила при
    загрузке, не через JS (срабатывает уже постфактум).
  На YouTube слой 3 отключён, чтобы не тормозить его.

Слой 4. CSS-скрытие.
  Общий набор правил (классы и id вроде .b-adv, [id*="yandex_rtb"], [class*="-ad-"], ins.adsbygoogle,
  [id*="adfox"], ссылки на букмекеров и т.п.) добавляется как <style id="ultralight-css">.
  Для YouTube — отдельный набор (<style id="ultralight-yt-css">): ytd-ad-slot-renderer,
  баннеры, промо-карточки и карточки рекламы в сетке (через :has()). Сторож раз в секунду
  возвращает <style>, если сайт его удалил.

Слой 5. Ручное скрытие (для того, что пролезло).
  Ctrl+Shift+X — режим выбора: элемент под курсором подсвечивается красным, клик скрывает его и
  сохраняет CSS-селектор; стрелка вверх выбирает родителя; Esc отменяет. Ctrl+Shift+Z — отменить
  последнее правило. Правила хранятся в localStorage под ключом ultralight_hidden и действуют
  только для текущего адреса сайта (origin). У сайтов, которые часто меняют зеркала, на новом адресе
  правила придётся задать заново.

Где править: список доменов — константа AD_HOSTS вверху main.rs (используется и в JS, и в DNS);
регулярное выражение — adRegex; CSS — переменные css и ytCss.


====================================================
7. YouTube: что делается и почему
====================================================
YouTube — сложное одностраничное приложение (SPA): оно само перестраивает страницу, меняет адрес без
перезагрузки (pushState / событие yt-navigate-finish) и использует Trusted Types. Реклама в нём
сегодня встроена в данные ответа сервера. Поэтому работа идёт на нескольких уровнях
(всё внутри функции setupYouTube, включается только на youtube.com / youtube-nocookie.com):

  1. Вырезание рекламы из данных. Перехватываются ytInitialPlayerResponse и ytInitialData (через
     setter на window), ответы /youtubei/v1/player|next|browse|search|reel (Response.prototype.json)
     и JSON.parse для больших строк. Функция pruneAds удаляет поля adPlacements, playerAds, adSlots,
     adBreakHeartbeatParams и рекламные элементы лент (adSlotRenderer, promotedVideoRenderer и др.).
     Плеер не знает, что должна быть реклама, и не делает рекламных запросов — это надёжнее и менее
     заметно для YouTube, чем блокировка запросов (на сбой запросов YouTube реагирует окном про
     блокировщики).
  2. Запасной скипер (проверка каждые 250 мс). Если реклама всё же дошла: признак — класс
     ad-showing / ad-interrupting у #movie_player. Скрипт жмёт «Пропустить», глушит звук, ставит
     скорость 16x и перематывает рекламу в конец; после рекламы возвращает звук и скорость.
  3. Окно «блокировщики запрещены». Если появится ytd-enforcement-message-view-model — убирается
     вместе с затемнением, воспроизведение продолжается. Селекторы подобраны по памяти и могут
     устареть.
  4. H.264 вместо AV1/VP9 (константа FORCE_H264 = true). Скрипт сообщает странице, что AV1 и VP9
     не поддерживаются (MediaSource.isTypeSupported и canPlayType), и YouTube отдаёт H.264.
     Причина: на видеокартах без аппаратного декодирования AV1/VP9 видео декодируется процессором —
     Shorts подвисают, «звук есть, картинки нет». Цена: максимум 1080p (1440p/4K есть только в
     VP9/AV1). Отключить: FORCE_H264 = false.
  5. Синхронизация адреса. Для SPA адрес читается ПОСЛЕ оригинального pushState/replaceState
     (иначе во вкладках оказывался адрес предыдущего видео).


====================================================
8. Интерфейс и горячие клавиши
====================================================
Интерфейс — это HTML-элементы, добавленные в document.documentElement:
  - #light-browser-ui — панель: ряд вкладок (32 px) + строка с кнопками и адресом (43 px).
    Скрыта выше экрана, выезжает плавно.
  - #light-trigger-zone — прозрачная полоса 15 px у верхнего края; наведение мыши открывает панель.
    Панель скрывается, когда мышь ушла с неё (если поле адреса не в фокусе).
Панель создаётся один раз; если сайт её удалил, те же элементы возвращаются в DOM — сразу через
MutationObserver, плюс запасной сторож раз в секунду (он же проверяет подмену documentElement и
возвращает стили).

Кнопки: назад, вперёд, обновить (history.back / history.forward / location.reload).
Адресная строка: если введённое похоже на адрес (есть точка, нет пробелов) — переход на него
(без http добавляется https://), иначе — поиск в DuckDuckGo.

Горячие клавиши (регистрируются один раз, на window, в фазе capture, чтобы сайт не перехватил):
  Ctrl + L            показать панель и сфокусироваться на адресе
  Ctrl + T            новая вкладка
  Ctrl + Tab          следующая вкладка по кругу
  Ctrl + W            закрыть текущую вкладку (последняя — закрывает приложение)
  Alt + <- / Alt + -> назад / вперёд
  F5 или Ctrl + R     обновить страницу
  Ctrl + Shift + X    выбрать элемент, чтобы скрыть
  Ctrl + Shift + Z    отменить последнее скрытие

Для YouTube важно: поле адреса находится в обычном DOM (не в Shadow DOM), поэтому горячие клавиши
самого YouTube (пробел, k, f и т.д.) не срабатывают, пока вы вводите адрес.


====================================================
9. Принятые решения и их причины
====================================================
  - Один WebView вместо вкладок-движков: экономия памяти и кода (подробности в разделе 1).
  - Интерфейс внутри страницы, а не нативный: не нужны тяжёлые GUI-библиотеки. Цена — защита от
    сайтов (см. ниже).
  - replaceChildren() вместо innerHTML = '': YouTube включает Trusted Types, и присвоение строки в
    innerHTML бросает ошибку — из-за этого панель вкладок на YouTube оставалась пустой.
  - MutationObserver + сторож вместо одного таймера: интерфейс возвращается мгновенно, а не
    в течение секунды. Ссылки на элементы переиспользуются, а не создаются заново.
  - Горячие клавиши навешиваются один раз: раньше каждая пересборка интерфейса добавляла ещё один
    обработчик, и Ctrl+T открывал сразу несколько вкладок.
  - Адрес синхронизируется после оригинального pushState: иначе в tabs попадал устаревший адрес.
  - SYNC_URL только из главного окна: iframes (в том числе рекламные) иначе записывали свои адреса
    во вкладки.
  - Вырезание рекламы из данных YouTube вместо блокировки запросов: надёжнее, не вызывает окно
    про блокировщики, экономит память (не создаются рекламные видео и карточки).
  - JS-заглушка автоплея убрана: она блокировала play() на каждый новый адрес, из-за чего Shorts
    не запускались при прокрутке, и не всегда срабатывала. Осталась настройка движка
    .with_autoplay(false). Её точное поведение зависит от версии wry и политики WebView2:
    возможно, это не строгий запрет, а политика Chromium по умолчанию. Проверить на практике.
  - H.264 вместо AV1/VP9: см. раздел 7, пункт 4.
  - DNS-блокировка на Windows: режет все типы запросов дешевле и надёжнее, чем JS; JS-слои остаются
    для других платформ и как вторая линия.
  - js_str(): экранирование адресов при подстановке в JS, иначе апостроф ломал выполнение скрипта.
  - Версия tao 0.23: совместимость с wry 0.35.0.


====================================================
10. Известные ограничения и риски
====================================================
  - История общая для всех вкладок. Вкладки — это просто смена адреса единственного WebView,
    поэтому «Назад» после переключения вкладки возвращает страницу другой вкладки, и адрес текущей
    вкладки в списке меняется. Решение: хранить историю каждой вкладки в Rust (раздел 12).
  - Переключение вкладки = полная перезагрузка страницы: теряются прокрутка, время в видео, текст
    в формах. Это цена низкого потребления памяти.
  - Интерфейс живёт внутри страницы. Сайт, который вычищает DOM или перехватывает события, всё
    ещё может мешать (хотя сторож и Observer это сильно ослабляют). Радикальное решение — вынести
    панель в отдельный нативный child-webview (в wry 0.35 поддержку надо проверять).
  - window.open всегда возвращает null: ломаются входы через всплывающие окна («Войти через
    Google», некоторые платёжные формы). Нужна доработка (открывать в новой вкладке).
  - Блокировщик не гарантирует 100% результата. YouTube регулярно меняет структуру данных и
    борется с блокировщиками; часть рекламы может быть встроена прямо в видеопоток — её из данных не
    убрать (тогда помогает только запасной скипер, и с задержкой). Селекторы окна «блокировщики
    запрещены» могут устареть. На других сайтах всё зависит от списка доменов и селекторов.
  - DNS-блокировка работает только на Windows. Синтаксис --host-resolver-rules и сам вызов
    with_additional_browser_args проверены по документации wry, но не на практике.
  - Ручные правила скрытия привязаны к адресу сайта (origin).
  - FORCE_H264 ограничивает качество 1080p.
  - Цифры потребления памяти (40–60 МБ) — целевые ориентиры, не измерения.
  - Закрытие последней вкладки закрывает приложение (так задумано).
  - При отключённых devtools (with_devtools(false)) отлаживать страницу нельзя.

====================================================
12. Идеи развития (по убыванию пользы)
====================================================
  1. Историю навигации хранить отдельно для каждой вкладки в Rust.
  2. Названия вкладок (document.title) и иконки сайтов вместо домена.
  3. Восстановление вкладок после перезапуска; сохранение прокрутки и времени видео при переключении.
  4. window.open: открывать в новой вкладке вместо блокировки; обработка target="_blank" через
     обработчик нового окна wry.
  5. Путь профиля — рядом с exe или в папке данных пользователя (а не относительно рабочей папки).
  6. Файл настроек (config.toml): переключатели блокировщика, FORCE_H264, поисковая система.
  7. Список рекламных доменов и селекторов подгружать из файла (фильтр-лист), а не из исходника.
  8. Скипер YouTube: ограничить только нужными страницами, сузить CSS-селекторы с подстроками
     ([class*="-ad-"], [id^="ad_"]) — они дороги по процессору на больших страницах.
  9. Закладки, история, загрузки файлов (with_download_started_handler), зум Ctrl +/−/0, F11,
     картинка в картинке, HTTPS-only, Ctrl+Shift+T (вернуть закрытую вкладку).
 10. Иконка окна (tao Icon) и метаданные exe (ProductName, FileDescription) через winres.

13. Памятка тому, кто будет менять код
====================================================
  - Весь JavaScript — внутри Rust-строки r#"..."# в main.rs. Нельзя использовать последовательность
    "# внутри JS (она закроет строку). Используйте одинарные кавычки; для селекторов вида #id
    пишите '#' внутри одинарных кавычек.
  - Метка __AD_HOSTS__ в JS заменяется Rust-кодом на список доменов. Если запускать JS отдельно
    (например, для проверки node --check), сначала подставьте любое значение вместо метки.
  - Код выше строки «if (window !== window.top) return;» выполняется и в iframes; ниже — только в
    главном окне. Не пишите в IPC из фреймов.
  - Функции, использующие ui (панель), должны выдерживать ui === null (интерфейс создаётся позже,
    чем часть хуков).
  - Любое присвоение HTML строкой на YouTube ломается из-за Trusted Types — используйте
    createElement, textContent, replaceChildren.
  - Как искать рекламу, которая осталась: временно включите .with_devtools(true) в билдере,
    нажмите правой кнопкой по баннеру -> «Просмотреть код», посмотрите тег, class/id и домен, с
    которого грузится. Домен добавьте в AD_HOSTS; точный элемент — в css (или скройте его
    через Ctrl+Shift+X). Для YouTube смотрите имя рендерера (например, ytd-...-renderer) и класс
    у #movie_player во время рекламы.
  - После любых правок JS проверяйте: извлечь текст из r#"..."#, подставить метку и прогнать
    node --check, затем cargo build --release.
  - Если меняете tao или wry, обновляйте обе версии согласованно и перепроверяйте импорты
    (WebViewBuilderExtWindows и др.), так как API меняется между версиями.
